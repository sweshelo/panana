# カスタムステージ配信: 追加行の所有とテクスチャ差し替えの計画

記録日: 2026-11-26。設計の整理と計画で、実装はまだない。配信側 `lanai-custom-stages` (`3ds/runtime/lanai.c` など) はこの作業の時点で読めなかったので、ランタイムの挙動は Panana 側のコードから推測した部分を含む。推測は「未確認」と書く。

## 現状

### 配信の仕組み (Panana 側から見える範囲)

- Panana は「配信用の zip」(`LanaiSession.distributionZip`) を書き出す。master は `LANAI_DELIVERABLE_TABLES` (Contents, MapStageIntegration, MessageMapStage, MessageMapName, ItemData, ItemDataCore) の変更だけを持ち、ほかの表は ROM のまま。`exefs/code.ips` は入れない。条件スクリプトがあると書き出さない。
- ランタイムはこの 6 表の行をゲームの master に重ねる (`lanai.c` の `master_header`)。それ以外の表の行を持つステージは丸ごと拒否する。
- ランタイム自体は `code.ips` として起動時に入る。配信で届くのはデータだけで、本体コードは更新されない。
- `lanai-stage.json` (`LANAI_STAGE_MANIFEST`) がステージのキーと、そのステージが所有するフラグの範囲を配信サーバーに伝える (`stageScript.ts`、`MAX_OWNED`)。

### できないこと

- 既存の行の変更 (例: 既存モンスターの能力)。
- 6 表以外への行の追加 (例: MonsterParameter / MonsterGroup / MonsterDesign へのモンスターの追加)。
- 既存のルートアーカイブの変更 (例: モンスターのテクスチャ BCH の追加)。

### Panana のモンスター追加 (通常 MOD)

- `lanaiCopyMonster` (`monsterCopy.ts`) が MonsterParameter の行を末尾に複製し、能力の行も別に持たせる。図鑑番号 (+0x00 bit 10-19) は 0 にする。
- 見た目は MonsterParameter +0x00 bit 20-29 の **MonsterDesign の行番号** (10 bit。ROM は 570 行)。MonsterDesign は +0x08 モデル、+0x0C テクスチャ、+0x10 戦闘モーションの BCH を、ルートアーカイブ 28480000 (Base) / 719F0000 (Update) のエントリのハッシュで指す (`monsters.ts`)。
- 群れからの参照は行番号。`ScriptMap::EncountBoss` 系の `FUN_0031C038` は 0x80000000 未満を行番号、以上を行 ID として引く (`lanai-stage-authoring.md` の battle())。

## 方針

1. **既存の行は変えない。追加の行だけ許す。** 既存のステージが参照する行のバイトを守り、実行中に配信しても既存の行へのポインターが無効にならないようにする。
2. **追加の行は ZIP (ステージ) ごとに番号の範囲を所有する。** フラグの範囲と同じ方式で、配信サーバーが範囲の重なりを拒否する。ほかの ZIP の有無や適用の順番で、行番号が変わらないようにする。
3. **ZIP ごとに独立して有効・無効にできる。** 外した ZIP の範囲は穴として残り、ほかの ZIP の行番号は動かない。

## 設計

### 番号の範囲

- 表ごとに「配信用の領域」を決める。ROM (Update) の行数の直後から、表の上限まで。
- ZIP は表ごとに `[start, start + count)` を所有する。マニフェスト (`lanai-stage.json`) に表名・開始・個数を書く。フラグの範囲と同じく、サーバーが割り当てて重なりを拒否する。
- Panana は、配信用の編集モードで追加する行の番号を、その ZIP の範囲から振る。範囲外の番号を参照する行 (群れ → モンスター、モンスター → 見た目など) は書き出し前に問題として出す。
- **行番号の上限**: MonsterParameter → MonsterDesign は 10 bit なので、MonsterDesign は 1024 行まで (配信用の残りは約 450 行)。ほかの参照も bit 幅を調べ、表ごとの上限を決める。全 ZIP がこの上限を分け合うので、1 ZIP の既定の割り当ては小さくする。

### ランタイムでの組み立て (案)

- 表ごとに「ROM の行 + 配信用の領域全体」の大きさのバッファを用意し、有効な ZIP の行をその範囲の位置に置く。
- **穴** (どの ZIP も使っていない番号、外した ZIP の範囲) は埋め草の行にする。埋め草は、全件を走査する処理に現れない値でなければならない (例: 図鑑番号 0)。表ごとに決める。
- 行数を「最後の有効な行まで」にするか「領域全体」にするかは、問題 1・2 (下記) の調査結果で決める。
- 行 ID (0x8000xxxx) で引く参照があれば、`FUN_0031C038` が行 ID をどう探すか (線形か二分探索か、整列が前提か) を確認する。整列が前提なら、ID も範囲で割り当てて昇順を保つ。

### 調べること (表ごと)

| 問題                | 内容                                                           | 影響                                                                                 |
| ------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 1. 先頭・行数の保持 | 起動時に表の先頭アドレスや行数を保持する処理があるか           | あると、実行中の追加が見えないか範囲外を読む。その表は起動時に適用するか再起動が要る |
| 2. 全件の走査       | 図鑑・一覧・ショップ・抽選など、全行を数える・選ぶ処理があるか | 追加の行や埋め草がほかのステージに現れる                                             |
| 3. セーブの添字     | 行番号を添字にする固定長のセーブ配列があるか                   | 上限を超える番号で範囲外に書く。ZIP を外すと番号の指す先が変わる                     |
| 4. 参照の bit 幅    | 行番号を持つフィールドの幅                                     | 範囲の上限                                                                           |

今の 6 表は実行中の追加が動いているので、問題 1 をどう避けているかを `lanai.c` で確認し、モンスター系の表に広げられるかを判断する。

## テクスチャだけ差し替えるときのリスク

モデル (+0x08) と戦闘モーション (+0x10) は既存のまま参照し、テクスチャ (+0x0C) だけ新しい BCH にする場合。

### 置き場所 (最大の問題)

- 既存のテクスチャは 28480000 / 719F0000 のエントリ。ゲームがテクスチャのハッシュを **どのアーカイブから探すか** は未確認。この 2 つに固定なら、新しいテクスチャを足すことは既存アーカイブの変更になり、方針 1 に反する。
- 回避案:
  - ゲームが探すアーカイブの一覧に、ZIP の新しいルートファイルを加えるフック (コードの変更。配信用のランタイムに入れる)。
  - ハッシュの検索が失敗したときだけ、配信の新しいファイルを探すフック (既存のテクスチャの解決は変わらない)。
- どちらもランタイムの変更が要る。データの追加だけでは済まない。

### BCH の中身

- **テクスチャの名前と数**: モデルのマテリアルはテクスチャを名前で引くはず。名前・数が元のテクスチャ BCH と一致しないと、テクスチャなし・別のテクスチャ・クラッシュになり得る。差し替えは「元の BCH の画素だけを入れ替える」形が安全。
- **形式と大きさ**: 元と同じ画素形式 (ETC1 / ETC1A4 / RGBA など)・同じ幅と高さ・同じミップマップ数にする。大きくするとメモリ・VRAM の確保量が変わる。戦闘では複数のモンスターが同時に読まれるので、元より大きいテクスチャは避ける。
- **BCH の版と再配置**: FREE! の BCH は H3D 0x21。ヘッダーの再配置表・各セクションのオフセットを壊さないこと。画素の部分だけを同じ長さで書き換えるなら、構造は変わらない。
- **アルファと UV**: モデルの UV 配置 (アトラス) は変えられない。透過の使い方 (アルファテスト・ブレンド) もマテリアル側で決まる。元にない透過を足しても効かない。

### 共有と状態

- **同じモデルの別のモンスター**: モデルを共有するモンスター (おおくちばしとアイスバードなど) は元のまま。新しい MonsterDesign の行がテクスチャだけ別のものを指すので、既存のモンスターには影響しない。ただし MonsterDesign の行を追加するので、上の範囲の割り当てが要る。
- **読み込みのキャッシュ**: ゲームがテクスチャをハッシュで読み込み済みとして使い回すと、同じ戦闘に元のモンスターと新しいモンスターが並んだときに、どちらかのテクスチャが使われる恐れがある。新しいテクスチャのハッシュは元と別にする (既存のハッシュの付け方に合わせ、ほかの ZIP とも重ならないように)。
- **ほかの画面**: 図鑑・下画面などが戦闘とは別の画像 (アイコン等) を使うなら、テクスチャを変えてもそちらは元のまま。どこが MonsterDesign +0x0C を使うかは未確認。

### Panana 側で必要なこと

- 元のテクスチャ BCH を写し、画素だけを差し替える書き出し (形式・大きさが一致しない画像は拒否)。
- 新しいテクスチャの置き場所は、上の「置き場所」の調査結果に合わせる。

## 手順

1. **ランタイムの確認**: `lanai.c` の `master_header` を読み、6 表の追加行が実行中にどう効いているか (問題 1 をどう避けているか) を確かめる。
2. **最小の実験**: MonsterParameter と MonsterGroup に 1 行ずつ足し、ゲームを起動したまま配信して、Azahar で戦闘・図鑑の数・セーブの再開を確認する。見た目は既存の MonsterDesign の行のまま。
3. **表ごとの調査**: MonsterParameter / 能力の表 / MonsterGroup / MonsterDesign について、上の表の問題 1〜4 を調べる。結果をこのノートに追記し、許可する表と埋め草の値を決める。
4. **範囲の割り当て**: マニフェストに表ごとの範囲を加え、配信サーバーが重なりを拒否する。Panana の配信用の編集モードで、追加の行をその範囲から振り、範囲外の参照と既存の行の変更を問題として出す (今の `distributionMaster` は表ごとに丸ごと比べているので、行単位の比較にする)。
5. **ランタイムの組み立て**: 有効な ZIP の行を範囲の位置に置き、穴を埋め草にする。ZIP の有効・無効で、ほかの ZIP の行番号が変わらないことをテストする。
6. **テクスチャ**: ゲームがテクスチャのハッシュを探す処理を調べ、置き場所を決める。決まったら、画素だけを差し替える書き出しと、ランタイムのフック (必要なら) を実装する。
