# モンスターのモーション (ミュージアム・戦闘) の解析と、図鑑での再生の検討

code.bin (v1.1.0) を逆アセンブルして調べた結果。アドレスは仮想アドレス (code.bin オフセット + 0x100000)。
§5・§7 は実データ (`56562135`、`470D2848`) で確かめた。

## 結論

- **再生できる見込みが高い。** モンスターのモーションは、図鑑がすでに読んでいる bcres (MonsterDesign +0x10、`470D2848`) の中の CGFX アニメ (CANM) で、コードが別のデータから作っているわけではない。
- ゲームはモーションを **アニメ番号** で指定する。番号はマスターのアニメ表 (テーブルのハッシュ `0xB3314000`) の行で、その行の名前と一致する CANM をモデルから探して再生する。
- **ミュージアムはアニメ番号 0x41** を再生する。戦闘の待機も同じ 0x41 (MonsterParameter +0x4A の bit3 が立っている個体だけ 0x42)。
- Panana 側で必要なのは、CGFX の骨格アニメ (と、必要ならマテリアル・表示のアニメ) の読み込みと、スキニングの実装 (§6)。

## 1. アニメの再生の仕組み

### 1.1 再生関数

| 関数 | 内容 |
|---|---|
| `FUN_003189b4(obj, 番号, ループ, s0 速さ, s1 開始フレーム)` | 本体。アニメ表の行を引き、モデルに再生させる (`FUN_0033555c` → `FUN_001213b8` / `FUN_0012d094`)。obj +0x50 に番号を記録する |
| `FUN_00311908(obj, 番号, ループ, s0, s1)` | 番号が 0 または今と同じなら何もしない版 |
| `FUN_0030ccac(obj, 番号, ループ, s0, s1)` | 同じ番号が再生中で、速さも同じなら何もしない版 (戦闘で使う) |
| `FUN_0031c834(ハンドル, 番号, 0)` | イベントスクリプト用 (`docs/events.md` の 0x52〜0x57 はこれ) |
| `FUN_0030d23c(obj, 番号)` | そのアニメをモデルが持っているか (`FUN_002f11ec`) |

ループ引数: 0 = 表の既定 (行 +8)。hardfp なので速さ・開始フレームは s0 / s1 で渡す。

### 1.2 アニメ表 (マスター +0x1C)

- 実行時マスター (`*0x520448`) の +0x1C のテーブル。`FUN_0031cfb8(holder, 番号)` で行を引く。
- 束縛は `FUN_0019643c(テーブル, ハッシュ)` の switch (ハッシュ → マスターの欄)。記号実行で解くと、+0x1C に入るのは **ハッシュ `0xB3314000`** のテーブル。
  - 同じ方法で既知の欄も確認できた: +0xE0 actionData = `5F37A400`、+0x914 MonsterDesign = `C402F800`、+0x94C MonsterParameter = `D6F5B800`、+0x310 treasureGroup = `05596800`、+0x32C mapChara = `1371BC00`、+0x380 mapResource = `A6460400`、+0x3D4 mapObject = `485D1800`、+0x540 mapParts = `ED105C00`、+0x1DC = `CFCDDC00` (状態の表と推定)。
- 行の欄 (行サイズは未確認):

| 位置 | 内容 |
|---|---|
| +0x00 | アニメの名前。ファイル内オフセットで、読み込み時にポインタへ再配置される (GS テーブルのヘッダー +0x18 / +0x1C の再配置表、`FUN_0019d564`) |
| +0x04 | f32。切り替え時の補間フレーム数と推定 (`FUN_002fc038` に渡す) |
| +0x08 | u8。既定のループ (0 のときは CANM の設定に従う) |

### 1.3 モデル側での照合

- モデルのノード +0x64 / +0x6C / +0x74 がアニメの 3 つのスロット (骨格・マテリアル・表示と推定)。`FUN_002f11ec` は 3 つとも見て、どれかに同じ名前のアニメがあれば「持っている」とする。
- 照合 `FUN_0032fff8`: スロットのアニメ (`+0x54` = CANM の先頭) の **名前 (CANM +0x08) の先頭 4 バイト** と、表の名前の先頭 4 バイトを比べる。
  - つまり 1 つの番号で、同じ名前の骨格アニメとマテリアルアニメ (目パチなど) を同時に動かせる。
- CANM の +0x10 (u8) がループ、+0x14 がフレーム数 (`FUN_00330048`)。

## 2. ミュージアム

- 画面のクラス: レイアウト `musiam_top_mons` / `musiam_1_list` などを使う (`FUN_0034e1d0` 付近。図鑑のセーブ変数 0x6B を読む)。
- 一覧は `FUN_002be9bc` が MonsterParameter を走査して作る。1 件 = {種族, デザイン (+0x4C), …, MonsterDesign +0x04 (説明), **MonsterDesign +0x34 (拡大率)**}。
- モデルの表示 `FUN_0034e0a4`:
  1. `FUN_002f2850(デザイン, 2, 0x200, 0)` でモデルを作る。
  2. 位置 (0, −20, 0)、回転 0。
  3. 拡大率 = MonsterDesign +0x34 × 0.85。
  4. **`FUN_00311908(model, 0x41, 0, 速さ 1.0, 開始 0.0)`**。
- 電波人間 (`musiam_top_antena`) の側は `FUN_0034b764` でアニメ 0x0B (ループ 2)。

## 3. 戦闘

### 3.1 モデルの生成 (`FUN_00289524`)

- MonsterParameter +0x4C → MonsterDesign の行。`FUN_002f2840(デザイン, 0x27, 0)` = `FUN_002f2850(デザイン, 2, 0x27, 0)` でモデルを作る。
- 戦闘の表示ユニット (基底クラスのコンストラクター `FUN_002f37e4`、vtable 0x4FCD2C。モンスターは 0x4FB908、味方は 0x4FBEA0) に次を入れる。

| 欄 | 値 | 意味 |
|---|---|---|
| +0x1D7 | **0x41** (MonsterParameter +0x4A bit3 が立っていれば **0x42**) | 待機モーション。何もしていないときに戻るモーション |
| +0x1D8 | 0x49 | 未確定 (被弾・倒れるなどと推定) |
| +0x1D9 | 0x4A | 未確定 |
| +0x18F | 6 | 既定の「表情」(§3.3) |
| +0x1DA | 0 | HP 0 のときのモーション (後で設定される) |

- `docs/battle.md` の「+0x4A bit3 = 戦闘の表示の切り替え (意味は未確認)」は、**待機モーションを 0x41 → 0x42 にする** ビット。
- 開始時に、フレームを乱数 × フレーム数に飛ばす (`FUN_002e800c`)。敵がそろって動かないようにするため。ミュージアムは 0 から。

### 3.2 モーションの切り替え (`FUN_002f3d1c(unit, 番号, 遅延, 表情)`)

- 番号 ≠ 0: 遅延フレーム後 (`FUN_00207fac`) に `FUN_0030ccac(model, 番号)` で再生する。
- 番号 = 0: 待機 (+0x1D7) に戻す。HP ≤ 0 なら +0x1DA を再生する。
- 呼び出しで使われている番号: 0x13、0x0E、0x15、0x17、0x18、1 (遅延 0x14)、アクションの演出 `FUN_001dd694` で 0x44 (行動 0x188 / 0x19B)、`FUN_001c0f9c` で 2 (行動 0xEB / 0xEC)。どれがモンスターに効くか (味方用か) は、アニメ表の名前とモデルの CANM を突き合わせて確かめる。
- MonsterDesign にはモーション番号の欄は見つからなかった。モンスターごとの違いは、bcres に入っている CANM の違いで出していると考えられる。

### 3.3 表情 (参考)

- 表示ユニットの仮想関数 +0x1C (モンスター `FUN_001c0ea4`) は骨格アニメではなく「表情」を切り替える (`FUN_00311880` → `FUN_002ff6f4`、表 0x5E755C)。既定は 6。
- 状態異常のときは、状態の表 (+0x1DC) の行 +0x3A の表情を使う。

## 4. MonsterDesign の欄 (モデルまわり、`FUN_002f2850` から)

| 位置 | 内容 |
|---|---|
| +0x10 / +0x14 | モデル (種類 3) / テクスチャ (種類 9) の bcres (`470D2848`) |
| +0x18〜+0x24 | f32 ×4。演出の種類 0x45〜0x48 ごとの距離 (`FUN_001dd694`) |
| +0x28 | 拡大率 (フラグ 0x10、フィールド)。今のマップ (var 0x50) が `A8654391` / `09A1DA1B` のときは +0x2C |
| +0x30 | 拡大率 (フラグ 0x20、**戦闘**) |
| +0x34 | 拡大率 (フラグ 0x40。**ミュージアム**はこれ × 0.85) |
| +0x3C / +0x3E | u16。ユニット +0x180 / +0x184 (演出の高さなど) |
| +0x40〜+0x5F | s16 ×4 ×4 (`FUN_002f2e74`、取り付け位置と推定) |
| +0x66 | u16 (> 200 なら半径に使う) |
| +0x68 / +0x69 | u8。追加の処理 (`FUN_00195224` / `FUN_001c1e18`、後者は `470D2848` から別モデルを読む) |
| +0x6E | u8。種類 (1/2, 4, 6, 8, 0xA, 0x10, 0x14) で影の大きさなどを変える |

フラグ bit0 = 影 (`50B5A9DF` の `05493800`)、bit1 = ボーン `waist` を探す、bit2 / bit3 = 影の拡大率。

## 5. ROM での確認手順

1. マスター `56562135` (なければ他のアーカイブ) から、エントリのハッシュ `B3314000` のテーブルを探す。行 0x41 / 0x42 / 0x49 / 0x4A / 0x44 などの名前を読む。
2. (確認済み) `470D2848` のモデルの bcres には、`001_E03_wait`、`002_E03_wait`、`003_E03_walk`、`004_E03_run`、`005_E03_SkillA`〜、`008_E03_damage`、`009_E03_down` のような骨格アニメと、`001_E03_eyes.cmtsa` (目) / `101_E03_02.cmcla` (色) のようなマテリアルアニメが入っている。
   - 名前の先頭 4 文字 (`001_`) が番号なので、ゲームが先頭 4 バイトで照合する理由も説明がつく。
3. (確認済み) アニメ表はマスター `56562135` の `animData.bin` (エントリのハッシュ `B3314000`、99 行 × 12 バイト、+0 名前・+4 f32 補間 0.2・+8 u8)。モンスターの行は次のとおり。

| 番号 | 名前 | 使われ方 |
|---|---|---|
| 0x41 | `001_` | ミュージアム、戦闘の待機 |
| 0x42 | `002_` | 戦闘の待機 (MonsterParameter +0x4A bit3 の個体) |
| 0x43 / 0x44 | `003_` / `004_` | walk / run (0x44 は行動 0x188 / 0x19B の演出) |
| 0x45〜0x47 | `005_`〜`007_` | skill A〜C |
| 0x48 | `010_` | skill D |
| 0x49 | `008_` | damage (表示ユニット +0x1D8) |
| 0x4A | `009_` | down (表示ユニット +0x1D9) |
| 0x4C〜0x50 | `101_`〜`105_` | 色のアニメ (`*.cmcla`、+8 = 2)。色違いの表示に使うと推定 (未実装) |

   - 0x01〜0x40 は電波人間などの番号 (`001_`〜`069_`)。モンスターと同じ名前でも、別のモデルの別のアニメを指す。
   - +8: 0 = CANM のループ設定、1 = 1 回 (skill / damage / down)、2 = 色のアニメ。

## 6. Panana での実装 (実装済み)

| 段階 | 内容 | ファイル |
|---|---|---|
| 1 | CGFX の骨格を捨てずに持つ (ボーン名・親・ローカルの拡大・回転・移動、逆バインド行列)。頂点のボーン番号と重み (スキニング 1 = 剛体、2 = スムース) も持ち、アニメするモデルでは静止姿勢に焼き込まない | `cgfx/cgfx.ts` |
| 2 | CANM を読む: DATA の辞書 9〜11。名前・ループ・フレーム数、ボーンごとのカーブ (定数 / ステップ・線形・エルミートのキー) と、ベイク済みの形式 (クォータニオン・行列)。参考は SPICA (GfxAnimation) と Ohana3DS | `cgfx/cgfx.ts` (新しく `cgfx/anim.ts`) |
| 3 | three.js: `SkinnedMesh` + `Skeleton`。TEV のシェーダー (`cgfx/tev.ts`) に three.js のスキニングのチャンクを足す。剛体スキニングだけのモデルなら、ボーンの `Object3D` にメッシュを付けるだけでもよい | `cgfx/three.ts`, `cgfx/tev.ts` |
| 4 | ビューア: `requestAnimationFrame` で進める。モーションの選択 (CANM の名前の一覧。アニメ表から「0x41 ミュージアム・待機」などの名前を付ける)、速さ、一時停止・フレームのスライダー | `pages/modelview.ts` |
| 5 | 表示の既定をミュージアムに合わせる: アニメ 0x41 をループ、拡大率は MonsterDesign +0x34。戦闘の待機 (0x41 / 0x42) にも切り替えられるようにする | `pages/monsters.ts`, `game/monsters.ts` |
| 6 | キャッシュ: `CACHE_VERSION` を上げる。アニメは Float32Array で持ち、ワーカーから転送する | `cgfx/loader.ts`, `cgfx/worker.ts` |

- 写真 (一覧の縮小画像) は今のまま静止姿勢でよい。0x41 の 0 フレーム目にしてもよい。
- マテリアルアニメ (テクスチャの切り替え・UV のスクロール) は、TEV の uniform を毎フレーム書き換えれば対応できる。まず骨格アニメだけで効果を確かめる。
- 注意: ゲームは名前の先頭 4 バイトで照合する。表示では完全一致で探し、なければ先頭 4 バイトで探す。

実装したもの: `src/cgfx/anim.ts` (読み込み・評価)、`src/cgfx/player.ts` (CPU スキニングと UV のアニメ)、`src/pages/modelview.ts` (モーションの選択・再生)。
スキニングは TEV シェーダーを変えずに、CPU で頂点を毎フレーム動かす。モデル 1 体なので十分速い。

## 7. CGFX のアニメの形式 (`470D2848` で確認)

- DATA の辞書 9 = 骨格アニメ (`SkeletalAnimation`)、10 = マテリアルアニメ、11 = 表示アニメ。
- CANM: +0x08 名前、+0x0C 対象のグループ名、+0x10 u8 ループ (1 = ループ)、+0x14 f32 フレーム数、+0x18 要素の辞書 (名前 = ボーン名 / マテリアルのパス)。
- 要素: +0x00 フラグ、+0x04 名前、+0x08 種類、+0x0C〜 スロット。
  - 種類 5 (骨格、カーブ): スロット 10 個 = 拡大 xyz、回転 xyz (ラジアン、R = Rz·Ry·Rx)、未使用、移動 xyz。フラグの bit (6 + i) = 定数 (スロットに f32)、bit (16 + i) = なし (静止姿勢の値)。それ以外はスロットにカーブへの相対ポインタ。
  - 種類 8 (骨格、ベイク): +0x0C 回転 (クォータニオン xyzw + u32)、+0x10 移動 (xyz + u32)、+0x14 拡大 (xyz + u32) の配列への相対ポインタ (0 = なし)。配列のヘッダー {f32 開始, f32 終了, u32, u32 フラグ} の後に (終了 − 開始 + 2) 個。ヘッダーのフラグ bit0 = 値が 1 個だけ (定数)。
  - 種類 3 (マテリアル、Vector2): `Materials["…"].TextureCoordinators[n].Translate` など。スロット 2 個、bit0-1 = 定数、bit2-3 = なし。
  - 種類 6 (色、`*.cmcla`)、種類 2 (表示、bool) は未対応。
- カーブ: {f32 開始, f32 終了, u32, u32, u32 区間数 (いつも 1), 区間への相対ポインタ}。
- 区間: {f32 開始, f32 終了, u32 フラグ} + 定数値、またはキー。フラグ bit0 = 定数、bit2-4 = 補間 (0 ステップ、1 線形、2 エルミート)、bit5-7 = 量子化。
  - キー: {u32 個数, f32 1/長さ, (量子化あり: f32 値の倍率, f32 値のオフセット, f32 フレームの倍率), キー…}。
  - 量子化: 0 Hermite128 (f32 ×4)、1 Hermite64 (u32 = フレーム 12bit + 値 20bit、s16 傾き ×2 / 256)、3 UnifiedHermite96 (f32 ×3)、4 UnifiedHermite48 (u16 フレーム / 32、u16 値、s16 傾き / 256)、5 UnifiedHermite32 (u32 = フレーム 8bit + 値 12bit + 傾き 12bit / 32)。2 / 6 / 7 は未使用。
  - **傾きには値の倍率を掛けない** (キーの差分から求めた傾きとの比が 1.00 になるのを全カーブで確かめた)。
- 静止姿勢: ボーンの拡大・回転・移動を親から合成したものが、保存されている逆行列 (+0xA4) と一致する (誤差 3e-5)。スキニングの逆バインド行列にそのまま使える。
- スキニング: モンスターの面グループの多くがスムース (種類 2、重みつき、最大 4 ボーン)。ほかは種類 0 (1 ボーン) と 1 (剛体)。
- アニメにだけあってスケルトンにないボーン名 (`cluster13Handle` など) は、書き出しの残りなので無視してよい。
