## 推奨する BIN 形式: PNSV v1 (試案)

マーカーは先頭の `PNSV` とブロック種別の FourCC に使う。**ペイロードからマーカーを検索して境界を推定しない**。アイテムや文字列にも同じバイト列が現れ得るため、索引の offset/length で読む。

すべて little-endian、ペイロード開始は 4 B 境界。ファイル上にポインタは保存しない。形式の上限は現在の PC 側試作で 16 MiB / 4,096 ブロック。これは ARM 側で確保する予算とは別で、実機ではさらに小さく制限する。

### 96 B のファイルヘッダ

| offset | 型/長さ | 内容 |
|---|---|---|
| 0 | 4 B | `PNSV` |
| 4 / 6 | u16 / u16 | major=1 / minor |
| 8 / 12 | u32 / u32 | headerBytes=96 / fileBytes |
| 16 / 20 | u32 / u32 | directoryOffset=96 / entryCount |
| 24 / 28 | u32 / u32 | generation / ファイル CRC-32 |
| 32 | u64 | Title ID |
| 40 | 16 B | MOD profile UUID の生バイト (文字列化しない) |
| 56 | 32 B | 最初の移行元の SHA-256。出自の識別用 |
| 88 / 92 | u32 / u32 | 予約 (v1 は 0) |

CRC は CRC-32/ISO-HDLC、対象はファイル全体、+28 の自身の 4 B だけを 0 として計算。破損検出用であり認証ではない。sourceDigest はその後も固定し、世代同期の代わりに使わない。u32 generation は単調増加、wrap は禁止し、上限到達時には明示した移行を行う。

### 各 32 B の索引エントリ

`{ FourCC tag, u32 id, u32 version, u32 count, u32 offset, u32 length, u32 crc32, u32 flags }`

- `(tag,id)` は一意。version はブロック内の形式、count はその形式が定める要素数。
- flags bit0 は「この版を理解できない読み手はゲームを開始してはいけない」。それ以外の bit は v1 では禁止。
- 未知の任意ブロックは PC 側でそのまま保持。必須ブロックの対応チェックは `assertSupportedSaveChunks` をゲーム状態へ適用する前に必ず呼ぶ。コンテナを読めたことだけで意味まで解釈できたとはしない。
- PC 側試作は版・範囲・重複・重なり・CRC を検証する。各ブロックの count とペイロードの意味、profile の一致、必要な必須ブロックの存在等は、今後の意味解析層で検証する。

### 予定するブロックとキー

| tag | 内容案 | 初期実装 |
|---|---|---|
| `LEGC` | 元形式のセーブイメージ全体。未解析バイト・内部の副本もそのまま保持 | 移行の非破壊検証と完全世代の基礎 |
| `MODS` | MOD UUID・定義版と、安定した論理キー → 実行時数値キーの対応表 | profile/ID の取り違え防止 |
| `VARS` | 拡張変数。索引 id が永続キー。各ペイロードは max・bitWidth・要素数・初期値・値配列を定義する予定 | まず追加ジャンプとストーリーフラグ。要素は RAM で直接引く |
| `ITEM` | 750 超のアイテム状態群、または既存キーの拡張尾部 | 後続段階 |
| `EVST` | 安定したイベント ID ごとの状態 | 後続段階 |
| `AMAP` | map hash ごとの踏破ビット列 | 後続段階、変数フックとは別 |
| `BYEX` | 呼び戻しの補助データ | 後続段階 |

この時点で実装したのはコンテナだけ。表内のブロックのペイロード仕様は未確定で、ゲームに読み込ませる形式はまだ公開 ABI として固定しない。

アイテムが後から増えても、他のブロックの意味を変えず、count/length とそのブロックだけを変更して再配置できる。値の並びには表の現在の順番ではなく、永続 ID を使う。削除時は欠番を残し、別の品目へ再利用しない。MOD の並べ替えによる ID 再割り当ては禁止。32 bit hash の偶然の一致に頼らず、MOD UUID と発行済みキーの台帳で衝突を検査する。

## ARM 側の負荷と互換性

JSON の解析コードを ARM に入れる必要はない。BIN なら必要な検査と読み込みが単純になる。ただし今回 JSON と BIN の速度・コードサイズは測定していない。「JSON なら必ずボトルネック」と断定する根拠にはしない。

索引の読み込み・検証・ID 対応は起動/ロード時だけ。毎フレームの読み書きで FourCC 探索、ファイル I/O、JSON、可変長リストの線形探索を行わない。既存キーは元の関数へ、拡張キー・拡張された添字は確保済み RAM の配列へ振り分ける。初期化前でも参照されるため、元の初期化と同じ段階でゼロ/初期値を用意する。

`key >= 150` の分岐だけでは、同じ `0x65` の添字 40 以降や同じ `0x26` の品目 750 以降は拾えない。新しいキーを割り当てて呼び出し側を差し替えるか、対象キーについて添字の境界でも分岐する必要がある。直接のブロック参照 (ユニット、オートマップ等) はさらに別経路。

また、低レベルの `FUN_00281E7C` は key (r1) と bit offset (r2) を受け、write `FUN_00281C70` は key (r1)、value (r2)、bit offset (r3) を受ける。ただし上位の配列アクセスはその前に定義を引き、count を検査する。#201 の「下位読み書き関数の冒頭でキーを比較」という案だけでは、新規 key の定義範囲外参照や拡張添字の早期拒否を防げない。定義を引く上位層も含めた adapter が必要で、下位フック2箇所だけで全拡張を解決できるとは扱わない。

既存のビット配置を変える場合は旧 flagData に従って値を取り出して新しい定義へ詰め直す。改変済み flagData で旧セーブを解釈してはいけない。未解析部分を再生成せず `LEGC` に保持し、後から仕様が明らかになっても失わないようにする。

## 保存と移行の手順

最終形の候補は ExtData 内の **完全な世代を持つ A/B ファイル** (`panana-a.bin` / `panana-b.bin`)。各ファイルに既存状態 `LEGC` と拡張状態を同梱する。元の savedata.bin と拡張 BIN を同時に更新できたと仮定してはいけない。

1. 起動時に Title ID、profile、必須版、長さ、CRC を検査し、有効な最新世代を採用。双方が有効で同世代・内容不一致なら異常として扱う。異なる profile のセーブを代替採用しない。
2. 初回は通常ロードが読む primary に加え、復元処理が読む secondary とその管理情報も保持し、元イメージの出自を記録して変換。独立解析で、通常ロードは primary、secondary は専用経路で読む意図的なスナップショットと判明した。既存形式を単なる世代順のA/Bとして解釈しない。拡張値にもこのゲーム内スナップショット/復元の意味を対応させる (ファイルの耐障害A/Bとは別の機能)。
3. 非アクティブ側へ、ゲーム状態の一貫したスナップショットを世代 +1 で書く。全バイト書けたこと、Flush/Close と再読検証が完了してから成功と扱う。既存の有効ファイルは先に消さない。
4. 次回は新しい完全世代を読む。途中失敗なら前世代へ戻せる。ただし 3DS の実際の書込み・キャッシュ・commit の耐障害性は実機で確認が必要。CRC と A/B だけで原子的保存が保証されたとはしない。
5. 新形式が一度確立した後の破損時は、古い元セーブへ無言で戻さない。復旧・古いセーブからの再移行はユーザーへ状態を示して明示的に行う。初回未移行と両方破損の識別方法も決める (profile 管理情報/移行記録)。

元セーブは少なくとも初回移行成功まで変更しない。外した MOD に戻す際は、バニラに存在しないマップ・アイテム等を含めた逆移行が必要。古い savedata.bin が自動で最新状態になるわけではない。

初期の疎通実験では通常セーブを正本のまま保ち、ExtData には診断値だけを書く。この段階は拡張セーブが完成した状態と区別する。拡張値を実際の進行に使う前に、完全世代のロード/セーブ・失敗時処理まで通す。

## Panana へ組み込む際の課題

- **ExtData**: #201 の CreateExtSaveData、exheader 権限、既存の `extdata:/kaharadata.dat` の用途を再確認。体験版引継ぎデータ等を壊さない。ID `0xA79` を使う際は既存アーカイブのファイル数/容量/用途と干渉しないか調べる。SD なし/満杯/権限なし/既存だが不足という別々の失敗を扱う。[libctru の公式ヘッダ](https://github.com/devkitPro/libctru/blob/master/libctru/include/3ds/services/fs.h) と [実装](https://github.com/devkitPro/libctru/blob/master/libctru/source/services/fs.c) も確認済み。CreateExtSaveData はディレクトリ数・ファイル数・容量・SMDH を指定し、IPC は `0x8510242`。ROM に libctru がリンクされているわけではないので、その IPC の構成・TLS のコマンドバッファ・fs セッションの扱いを既存コードと合わせる。外部実装が存在することは、このタイトルの権限で呼べる証明にはならない。
- **起動順序**: 「ゲームを始める準備をしています」表示時に移行してよいとはまだ確定していない。#201 の候補 `0x435490` は `FUN_002e28e0` 呼び出し前の関数途中で、ロード後の地点ではない。通常ロード・専用のスナップショット復元・新規作成・初期値参照の順序、タイトルへ戻る操作、ニューゲーム・削除を追う。
- **非同期保存**: `FUN_00290480` 等のワーカースレッドと状態を共有する。拡張値も同じ時点のコピーを取得し、終了/失敗を元の保存 UI に返す。メインスレッドの値を逐次読んでファイルへ書くと不整合になる。
- **パッチ共存**: v1.1.0 の元命令と既存 MOD の変更を検査する。コード cave、フック、BSS の確保を他パッチと取り合わない。ARM11/ARMv6K で動く命令のみ。既存の `mappatch.ts` 等の確保方法と統合する。
- **プロジェクト保存とゲームセーブの区別**: `src/session.ts` 等の編集プロジェクトには MOD の定義・永続キー台帳・必要なランタイム版を保存。個人の実セーブや ROM を MOD 配布物へ混入させない。
- **UI と export**: 未対応なら現状の枠上限を維持。#201 を必要とする編集ではパッチを export へ必ず含める。形式 codec があるだけで `AUTOMAP_LIMIT` やイベント枠の検査を消さない。
- **既存 main との差**: 作業ツリーには多数の既存変更があり、#199 の `jumppoints.ts` も現在のチェックアウトには無い。#199 の実装が入る基点を確定し、そこに後続パッチを統合する。今回既存変更の上書きや git の操作はしていない。

## 実装を進める順序と合格条件

1. 読み取り解析を再現し、通常 primary / 専用 snapshot restore という今回の結果を動作観測で検証する。3 番目のブロックと小ブロックの役割、key が分かる adapter 境界も確定する。
2. **使い捨ての Azahar プロファイル**で ExtData 不在から作成、ファイルの作成・読書き・再起動まで疎通する。ユーザーの現在のセーブで試さない。既存 ExtData がある状態も確認。
3. 既存イメージを無変更で `LEGC` に包み、PC 側でバイト一致の取り出しを確認。ARM 側も全ブロックを同じ世代から復元する。
4. MOD の安定キー台帳と `VARS` のペイロードを決め、追加ジャンプを **3 件以上** 保存・再ロードする。既存 38 行の訪問情報と W01/W02 の位置の対応も維持。
5. 新規ゲーム、既存セーブ移行、セーブ後のタイトル復帰・再ロード、profile 不一致、未知の必須版、片側/両側破損を確認。書き込み途中・容量不足の故障注入で最後に成功した完全世代が残ることを確認。
6. 実機で初期化・Flush/Close・再起動・SD なし等を確認してから配布。アイテム、イベント、オートマップ、呼び戻しの上限解放はそれぞれ別の検証課題として順次対応。

初期 #201 の完成条件は「ExtData にファイルができる」ではなく、**既存進行を保持して移行でき、追加ジャンプ 3 件以上と拡張変数を再起動後も復元でき、保存失敗で進行を壊さないこと**。
